# Teacher Pain Point Analysis

**ID:** PAIN-TEACHER-001  
**Status:** Draft — TLM-001

---

## Method

Each pain point is scored for product prioritisation:

| Field | Meaning |
|-------|---------|
| Current effort | How hard/long the workaround is today |
| Frequency | How often it hits |
| Impact | Effect on teacher wellbeing, teaching quality, or student outcomes |
| Estimated time lost | Directional hours lost (per event or per week) |
| Automation opportunity | What could be reduced by intelligent assistance + workflow |
| Priority | P0–P3 |

**Scale**

- Effort / Impact: Low / Medium / High / Severe  
- Frequency: Daily / Several× week / Weekly / Monthly / Termly / Yearly

## Time-loss rollup (directional)

For a heavily loaded class teacher + subject teacher:

| Band | Weekly hours lost to listed pains |
|------|-----------------------------------|
| Conservative | ~15 |
| Typical | ~20–28 |
| Peak exam weeks | ~35+ |

EduVijna does not need to eliminate all of this. Capturing **8–12 hours/week** back with quality intact would be extraordinary.

---

## Design implications

1. Attack P0 pains as a connected loop, not isolated tools  
2. Treat trust/explainability (PAIN-15) as a gate for all AI outputs  
3. Prefer workload deletion over dashboard addition  
4. Measure success as hours returned + approved output quality
